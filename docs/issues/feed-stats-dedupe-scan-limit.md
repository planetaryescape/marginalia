# Feed counts can over-count an article opened more than about 100 times

Status: done, 2026-10-29. Feed opens and finishes no longer read a window of rows.

## What was built (2026-10-29)

- `feedOpenCounts` (userId, articleId, optional sessionId, desk, visit; index `by_key`) holds, per reader, article and session (no session is its own key), the desk opens (no `visitId`) and reader-page visit opens. A new `opened` row bumps the right number, and the feed gains one only when `max(desk, visit)` rises, in the same transaction. Exact, O(1) and independent of row order.
- A repeated finish is found with the index `by_user_article_action_visit_counted`: a visit's finish counts only if no other `finished` row of that visit has already been marked. One lookup, whatever the row count.
- History is rebuilt, not reconciled. `feedStats` is derived data, so a version-2 rebuild (`feedStats.backfill`, state in `feedStatsBackfill` with `version`, `phase`, `cursor`, `seen`, `dirty`) clears the reader's `feedStats`, then `feedOpenCounts`, then every `feedCounted` marker, then recounts all interactions in creation order under the rules above. Every step reads at most 4 rows, so a transaction stays far from the 16 MiB read limit even with large `annotationsOpened` arrays and long article text. An earlier design that built a key's counter from its history on first touch was dropped after review: it double-counted rows an older version had credited, let a stale marker suppress a visit's only credited finish, and exceeded the read limit over large history.
- Live counting coordinates with the rebuild through the existing `feedCounted` marker. Until a reader is `ready` at the current version the live path counts nothing and leaves the row unmarked, so the rebuild counts it. A row whose creation time is at or before the rebuild's `seen` position (committed late, behind the cursor) sets `dirty`, and the rebuild makes another pass instead of finishing. The live path and the rebuild both read and write the state row, so the database orders them: a live row either sees `ready` or is reached by the rebuild. A reader with no history starts `ready` and is counted immediately. After the rebuild, the live path uses the counters.
- A rebuild cannot stall: each step is scheduled by one function that gives the state row a fresh `stepToken` (and cancels the step still pending), and a step whose token is not current does nothing, so a chain cannot fork. A live write that finds the rebuild unready and no step scheduled in the last minute (`scheduledAt`) reschedules, and `readers.setStatus` reschedules the pending rebuild when a reader is made active again. `feedSuggestions`, `taste` and the reporting stats read `feedStats` through `readableFeedStats`, which returns nothing while a reader's rebuild is not ready at the current version.
- Starting it: the first interaction of a reader with an old or missing state starts the rebuild, and `bunx convex run background:fanOut '{"job":"feedStats"}'` starts it for every active reader. It is not on a cron, so run that once after deploy. Bump `REBUILD_VERSION` in `feedStats.ts` to rebuild again under new rules.
- Known costs: counts for a reader read zero or partial from the start of their rebuild until it finishes (seconds for today's data), which can affect the feed suggestions that read `feedStats` in that window. Interactions on articles without a feed are never counted. Deleting a library purges `feedOpenCounts`.

## Why a different window doesn't fix it (2026-10-29)

Two attempts failed independent review. Reading the newest 200 rows instead of the oldest double-counts old pairs in the backfill. Reading only the interaction's own session, newest 200, still stops counting after about 100 pairs in one session, and every open without a session shares one bucket, so that is the same limit. Any truncated window computes ranks from a suffix that may start between a desk row and its visit.

## The fix when it's needed

Per article and session, the opens counted always equal the larger of the desk opens and the reader-page visits, whatever order the rows arrive in. Store those two numbers in a small table keyed by user, article and session. Count a new open when it raises the larger of the two, and update the row in the same transaction. Fill the table from history with a resumable backfill before the live path relies on it. A repeated finish needs the same treatment keyed by visit.

`isNewOutcome` in `packages/backend/convex/feedStats.ts` pairs a desk open with the reader page's checkpoint open, and drops a repeated finish for one visit, by reading the article's same-action interactions with `take(200)`. The index returns the oldest first, so once an article has more than 200 `opened` rows (about 100 opens, because each open is usually a desk row plus a visit row) a newer interaction is not in the window. The function then counts it unpaired, so the desk and visit rows of every open past that point each add to `opened`. The same cut-off applies to `finished`, though 200 finishes of one article is far less likely.

Likely cause for fixing it: scan newest first, or look up the partner row directly (same session, opposite kind, nearest in time) instead of ranking within a window. A per-session marker on the desk row would also remove the scan. Not fixed because no reader is near the limit; found in the second review of rung 2g.
